# 0.5.5 初稿质量门、问题画像与状态迁移

> 部署前备份持久数据卷以及两个二进制密钥文件。0.5.5签发新记录或下载链接后，禁止只把应用冷回滚到0.5.4：旧版在重启时会裁剪密钥边缘字节，可能无法验证0.5.5的新签名。若必须完整回滚，应同时恢复应用和与之匹配的升级前数据卷快照。

## Railway切换门禁

0.5.4与0.5.5不得混跑。Railway发布必须采用一次性单版本切换：先停止生产写入与新下载链接签发，排空旧请求并取得持久卷一致性快照；确认所有0.5.4实例退出后启动0.5.5；连续核验健康端点、18项工具注册和完整运行时证书均为0.5.5后，才迁移项目状态并恢复流量。禁止在旧、新实例并存的滚动窗口内执行迁移、生成、提交、审计或签发链接。

0.5.5首次启动会用raw-key HMAC写入独立安全epoch和旧下载令牌绝对截止（本次安装切换时刻＋24小时），再以`preparing → committed`事务完成初始化。旧令牌只在该安装级绝对截止前可用，重启不会延长；已提交epoch对应的截止记录缺失时启动失败，只有中断在`preparing`阶段才按同一截止恢复，绝不新开窗口。v2令牌只接受raw key。密钥缺失、过短或全空白，以及安全epoch或截止记录验签失败时均停止启动或拒绝下载，不得自动轮换。

安全epoch由同一持久卷中的三份相互校验记录共同保护：根目录`/.v055_security_epoch.json`、根目录`/.legacy_download_token_window.json`和`/projects/.v055_security_epoch.anchor.json`。备份、迁移和回滚时必须把三份记录连同项目状态纳入同一个一致性快照，并从同一快照整体恢复；不得单独删除、替换、重建或从当前时间重新签发其中任何一份。只要独立anchor仍在，根目录两份记录同时缺失也会失败关闭，不会续期。若操作者或存储故障把三份记录全部删除，而项目尚未迁移、仍声明0.5.4，程序无法把这种特权卷破坏与真正的首次0.5.5初始化区分开；这是明确的卷级灾难恢复边界。此时必须恢复包含三份一致记录及对应项目状态的完整快照，不能依赖服务识别或修复全删状态，也不得在该状态下恢复生产流量。

## 升级目标

0.5.5 把已经反复出现的问题从审计后的返工项前移为生成前约束和提交前硬门。独立审计继续保留，但其职责是查找生产与程序门禁可能遗漏的语义问题，不再承担清理转场重复、动态关键帧、9:16缺失、跨镜代指、禁词、虚假PASS等已知确定性错误的主要责任。

本次升级不修改历史分镜、工作簿或 canonical。所有旧 artifact、原始文件字节和历史指纹保持只读；迁移只更新当前项目中枢、问题台账契约和活动策略。

## 三个新增工具

| 工具 | 作用 | 写入边界 |
|---|---|---|
| `migrate_project_state` | 对0.5.4及更早的项目中枢/问题台账做计划、执行或受保护回滚 | 只写项目状态与签名迁移日志，不改历史产物 |
| `query_project_issues` | 按模式、状态、严重度等查询跨批次问题，并返回活动预防画像 | 只读 |
| `preflight_storyboard_draft` | 对 scene、episode 或 full 草稿执行与正式提交同源的 compact/R10-SPC-1/语义门禁 | 只写草稿预检证据和问题台账，不写正式产物 |

工具总数由15个增加到18个。

## 强制生产顺序

正式全量生成或完整场景/分集重建必须执行：

1. `get_agent_status(project_id)`。
2. 若状态为 `migration_required`，在明确授权的 `rule_improvement` 或 `version_management` 工单下先调用 `migrate_project_state(action="plan")`，核对兼容报告和前后哈希，再调用 `migrate_project_state(action="execute")`；重新取得有效、可执行状态。
3. `query_project_issues`，读取当前开放问题模式、已知复发和活动预防画像，将画像哈希绑定到生产工单。
4. 生成一份27字段 canonical；每完成一个场景，调用 `preflight_storyboard_draft(scope_kind="scene")`。失败则只修该场景并重检，不继续扩散。
5. 全部场景干净后，对完整 canonical 调用 `preflight_storyboard_draft(scope_kind="full")`。
6. 把返回的签名、full-scope、commit-ready `draft_preflight_id` 原样传入 `commit_storyboard`。项目、工单、canonical、规则、验证器、生产会话、预防画像或范围任一不一致都阻断提交。
7. 把不可变生产 artifact 和 handoff 交给独立审计 authority；它独立复算八层语义并签发最终证书。
8. 只有干净独审证书和用户明确签核齐全后才能归档。

失败的 scene/full 草稿会生成签名预检记录和问题台账 occurrence，但不创建 artifact、正式版本、XLSX、正式母版/GPT投影、successor pointer 或 handoff。这样既保留学习证据，也避免把失败草稿伪装成生产版本。

## 初稿质量合同

第一次提交的完整草稿质量结果不可被后续修补覆盖：

| 指标 | A级生产门槛 |
|---|---:|
| 总体正确率 | ≥98% |
| 直接可用率 | ≥98% |
| 每集正确率 | ≥96% |
| 新增局部问题率 | ≤2% |
| 硬错误 | 0 |
| 重大问题 | 0 |
| 已知问题复发 | 0 |
| 系统性重复模式 | 0 |

这些数字衡量“生成时是否已经正确”，不代表允许带着剩余问题发布。任何已检测问题都必须在 full preflight 前清零；只有 clean full preflight 才能签发 commit-ready 证书。

最终独立审计的标准不变且更严格：八层100%通过，阻塞错误0、原问题残留0、修改新增问题0。生产可以写 `生产预检通过｜待独立审计`，不得写 `审计通过` 或提前填入0问题。

## 跨批次问题模式

0.5.5 不再把 episode、filename、shot ID 或版本写入问题去重身份。稳定 pattern key 由项目、错误码、规范化字段类别和规范化根因/问题类型组成；位置字段作为 occurrence history 保存。

因此，同一个模板问题分别出现在EP01、EP05和EP09时，会得到一个模式、三个以上发生位置，而不是三个互不关联的单镜问题。重复发生会提高 recurrence/systemic 等级并进入下一次生成前的活动预防画像。

旧问题样本必须进入负向回归：历史失败样本必须FAIL，修复样本必须PASS；任一已知错误重新通过都会阻断部署或生产。

## 三方职责

| 角色 | 必须负责 | 禁止代替 |
|---|---|---|
| 生产/生成器 | 只创作一份 canonical；使用问题画像；逐场景修复；提交前清零 | 不得自行签发独审结论 |
| 确定性服务 | 状态迁移CAS、模式查询、全部门禁、静态投影、XLSX往返、质量计算、哈希/证书绑定、失败草稿记账 | 不得编造缺失剧情或语义事实 |
| 独立审计 | 读取不可变成品，独立复算八层，查遗漏并签发最终结论 | 不得重新生成、修改或替生产清理已知错误 |

## 迁移与回滚安全

- `plan` 不写状态，只返回候选差异和哈希。
- `execute` 需要有效完整运行时证书、授权工单和 compare-and-set；写入前后hub/ledger哈希及签名迁移日志。
- 同一迁移请求可安全重试；已经达到0.5.5的有效项目不会重复创建版本历史。
- 部分写入由迁移事务恢复；并发状态变化会失败关闭。
- `rollback` 只在当前状态仍精确匹配迁移后的两个哈希时允许，避免覆盖迁移后产生的新工作。
- 历史工单和交付若引用退休操作/输出，只标记 `legacy_read_only`，不删除、不改写历史证据。

## 发布验收

发布前必须完成：

- 全部现有测试和0.5.5迁移/预检/问题模式/状态语义回归通过；
- stdio 与 HTTP MCP 均发现18个工具且版本为0.5.5；
- 失败草稿确实不产生 artifact/version/XLSX/handoff；
- full证书在 canonical、规则、验证器、会话、工单、画像或范围不匹配时拒绝；
- 旧工作簿中的 legacy `PASS/0问题` 在没有有效独审证书时只显示为历史声明，当前有效状态为 `PENDING_AUDIT`；
- 迁移 plan/execute/幂等重试/受保护 rollback 均有签名证据；
- PR合并后Railway部署健康检查、完整自测和真实项目迁移通过；
- Skill、项目中枢与问题台账同步到同一0.5.5规则/验证器指纹。

0.5.4 的集成架构、0.5.3 的性能诊断、0.5.1 的十二项THG设计和更早迁移文档仍作为各自版本的历史事实保留，不进行全局文字替换。
