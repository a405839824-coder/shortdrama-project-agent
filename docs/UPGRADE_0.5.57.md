# 0.5.57 审计流程修复与部署边界

本版修复通用审计协议中的声音字段覆盖、实际工作簿证据引用、缺证结论与相邻镜机器证明接入。版本号同时更新管理员和员工共用服务；现有分镜模板、基础声线、保存原件与历史投影版本不变。

软件回归通过不等于分镜逐镜审计完成。既有失败、未知及撤回记录仍须保留，缺少来源或无法解析的状态不得改成通过。客户端必须读取 MCP 返回的完整 `content[].text`，不能以结构化摘要替代错误正文。

通过 `read_project_artifact(section="audit_contract")` 读取精确提交合同，通过 `audit_coverage:<collection_id>` 恢复已签原页及更正记录，均须跟随全部 `next_call`。完整分页提交 schema 由义务首页提供的精确调用读取，避免首个返回页面超过字符预算。`coverage_page.action=rebind` 必须携带原 `handoff_artifact_id`、原工单/审计周期、完整页清单及快照哈希；后续新页使用响应 `data.handoff_manifest.handoff_id`。旧记录保留，新集合从零检查开始。外部只读审计的文件级缺证和未完成检查保留在报告中，不据此虚构错误镜头或修复目标。明确错误仍可生成绑定具体镜头、字段的修复包，实际修改仍须另有显式授权的修复工单。

## Library 数据保护

当前 Library 模式使用 `/tmp/shortdrama-library-runtime/projects` 和同级 `exports` 保存已挂载数据；重部署可能清空这两个目录。`/data` 中的 Library 指针不能替代完整项目及导出文件备份。

本版启动恢复只接受 `/data/.upgrade-0557` 下、目标版本为 `0.5.57`、合同为 `library-runtime-transfer-0557-v1` 的签名归档。它验证整棵文件树、完整归档哈希及权限/密钥/指针指纹，原子发布到临时运行目录后消费清单。历史 `.upgrade-0556` 保持原样，已消费清单不会在以后冷启动时重放；当前归档也不能覆盖已有但不同的运行目录。

## 发布顺序

发布准备脚本位于工作区 `outputs/audit_flow_0557_release`。该目录只能保存本次新快照和回执，不复用上次部署快照。

1. 完成本次测试、独立代码复核与 PR 检查。线上读取当前 Railway 实例、0.5.56 版本、单副本和唯一入口；确认管理员及员工连接同一服务。保留确切 PR 编号和已审查完整 head SHA，尚不合并 PR。
2. 运行本次 `deploy_connected.py --instance <当前实例> --head <已审查完整SHA> --pr <PR编号>`。脚本核对当前 main 和 PR head，先建立维护连接，再隔离服务入口并等待在途请求结束，完整备份当前 `projects`、`exports`，验证新归档及受保护配置后才发出合并请求。无需输出 token 或密钥内容。
3. 合并触发部署后保持入口隔离。查询新部署成功与新实例，再运行 `read_deployed_state.py --instance <新实例>`，核对本次启动恢复、完整文件树与受保护配置。运行 `verify_release_readback.py`，将已部署源文件逐一与合并回执绑定的 Git blob 比较。
4. 仅在恢复、文件、配置和代码比对均通过后恢复原服务域名的自动端口，并回读入口。再用管理员及员工连接读取版本和运行时状态；之后才继续真实在线分镜审计。

合并提交的结果未知时，不取消已签名归档、不恢复旧写入入口，不重试合并。只有明确未提交或明确拒绝的合并，且旧写入器解除隔离回执证明当前清单未激活、未消费，才能恢复旧入口。部署脚本准备完成不表示已经部署；最终状态以本次线上回执为准。
