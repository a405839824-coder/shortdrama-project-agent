# ChatGPT plugin execution contract

## Non-negotiable proof of execution

- In every new chat, call `get_agent_status` before acting. Resume with the user's `project_id`; if none is known, inspect the returned project list and ask only when more than one plausible project exists.
- Verify that status explicitly advertises plugin `0.5.15`, exactly 19 tools including `recover_storyboard_handoff`, `output_contract=R10-SPC-1`, `window_neutral_orchestration=true`, and `window_role_restrictions=false` before accepting any service-authored storyboard workbook or formal/GPT projection. If status reports `migration_required`, ordinary production is disabled: use an authorized rule-improvement/version-management work order to plan and execute `migrate_project_state`, then obtain a valid status again. A valid older compact-master certificate may be used for project-state reads and migration coordination only. If the canonical can be read, apply the bundled deterministic R10-SPC-1 validation/export adapter and commit a compliant new version; if it cannot, record a capability gap and stop rather than deliver the old header, old timing stages, old lighting text, or deleted fixed phrases.
- Any mutating task must have a successful `begin_project_task` result. Content shown only in chat is not a persisted project change.
- A generated or changed deliverable exists only after a commit tool returns an `artifact_id`. State the returned ID and download link briefly.
- `commit_storyboard` returns an immutable production workbook whose audit overlay is `PENDING_AUDIT`/`未签发结论` with null counts and trace, not an independent audit verdict. `audit_storyboard` creates a new immutable signed-audit-overlay artifact/successor workbook and never edits the production XLSX in place. A storyboard may be archived only after its clean `independent_audit` certificate matches the exact canonical and raw artifact fingerprints, followed by the user's explicit `signoff_task` approval. Non-storyboard artifacts still use `complete_task_validation`.
- If a tool call fails or tools are absent, report the exact blocker. Never replace an execution result with a confident narrative.
- For novel/chapter input, no formal shot may be generated until the full authorized chapter has been synthesized into one chapter map with source treatment, protected dialogue, character state/cognition, adaptation budget, beat plan, and 100% preflight coverage.
- For every novel/script preflight, only the server-registered source file whose payload SHA, Hub authority entry and artifact-metadata role cross-bind is dialogue authority. The source-dialogue v6 closed grammar must enumerate exact audible occurrences and speakers without accepting candidate inventory, `source_lock`, ledger, cognition/anchor or storyboard names as parsing authority. Persist the authority manifest SHA in the preflight report and signed draft-preflight record: it directly binds source fingerprint, role, occurrences and grammar SHA; grammar SHA transitively binds implementation-source SHA, and artifact metadata references the signed record through `draft_preflight_id`. Any ambiguous cue, speaker residue, separator, quote/read-aloud boundary, or unsupported source form fails the entire preflight with no artifact, version, XLSX, projection, successor or handoff.
- The compact canonical has exactly 27 atomic shot fields. Every new write records `source_lock.output_contract=R10-SPC-1` and follows `strict_prompt_contract.md`: each shot's `生成限制` and both export projections explicitly contain `9:16竖屏`; GPT begins `画幅：9:16竖屏` and uses only the static whitelist; formal/GPT projections contain no literal `BGM` and use `禁止额外配乐`. The XLSX export has exactly these ten columns: `分镜序号｜时长｜累计时长｜功能类型/场景连续性ID｜正式分镜母版｜GPT关键帧生成指令｜参考图锚定｜覆盖原文｜原文依据类型｜原文支撑句`. There is no Seedance execution column or batch sheet. Export is blocked until THG-01–THG-12 and the actual multiline XLSX round-trip pass.
- For any public-flow scene, formal generation must load `public_scene_ecology.md` and include ordinary-person density, location roles, staggered actions, spatial layers, concrete near/mid/far ambience, dialogue ducking, and audiovisual source evidence in the same formal-master record. An empty public scene requires both a visible empty-state description and a plot-grounded reason.
- Give every authenticated user window the same orchestration access. Public `begin_project_task(action="create")` creates a window-neutral work order; any trusted window in the same OAuth namespace may create or continue production, audit, or repair. The transport session is request provenance, not role permission. Keep distinct server-minted production and audit work-order roots/window bindings/actor bindings, and start a separate repair authority only after audit fails and repair is authorized. The same ChatGPT window may request all three, but production preflight never becomes audit, audit never mutates, and repair returns to the original audit root and cycle.
- Do not use continuation for 0.5.14 window-neutral work orders. Preserve 0.5.11 continuation only for stored 0.5.13-and-earlier window-bound work orders under the exact legacy cloud role matrix: production `storyboard_create|storyboard_regenerate|storyboard_change`, independent audit `storyboard_audit`, or repair `storyboard_repair`. Do not continue `rule_improvement`, version management, another production-classified operation, or an arbitrary unfinished work order. Call `begin_project_task(action="plan_role_continuation")` for exactly one legacy `resume_work_order_id`, verify the server-derived role, stable `authority_root_id`, exact operation/mode/authorization and work-order contract, pre-state hash, current/next generation, `new_binding_status`, and `plan_sha256`, then execute with the identical request, exact hash, and `ROTATE_WINDOW_AUTHORITY_REVOKE_PREVIOUS_SESSION`.
- For legacy continuation, both plan and execute reject without writes while a role operation lease or an unexpired handoff, repair-package, or draft-preflight commit claim is live. The operation lease remains strictly exclusive per logical authority root; do not join same-root calls. Different authority roots may execute in parallel. All signed lineage, lease, claim-generation, expiry and fail-closed rules remain unchanged.
- Legacy execute appends a signed continuation and advances the unique active head to a new physical window/actor/session epoch under the same root. The previous generation is logically revoked by the head change without rewriting signed history. This compatibility path never assigns roles to a 0.5.14 user window and never closes an audit or project blocker.
- Claim every ordinary handoff, repair package and independent re-audit successor only under the claimant work order's current active authority root/generation/server-observed session, with a fresh token, monotonically increasing claim generation and bounded live lease. Finish and release must revalidate all of those fields under the project lock. An old generation, replaced token/generation, expired lease or prior session must fail with zero signed-storage and Hub mutation; expiry permits only a fresh current-epoch claim. Finishing an ordinary handoff also requires the actual service-stored signed `independent_audit` certificate whose certificate, handoff, work-order and artifact bindings all match. Never accept a caller label, production-preflight certificate, unsigned record or mismatched audit certificate.
- A delayed successor-candidate publication may advance only the candidate artifact transaction. If its signed handoff has already been claimed or consumed, preserve that handoff and its exact Hub projection byte-for-byte, including lifecycle, claim snapshot/history and audit-certificate binding; never replay an earlier `prepared` candidate over it. A passed `storyboard_audit` work order is continuable only for the narrow case of exactly one service-signed `prepared independent_audit_successor` already bound to that audit authority. The continuation may restore access to that route only; zero/multiple/unsigned/non-prepared routes fail without reopening PASS, changing the verdict or minting a second successor.
- Read `incremental_storyboard_execution.md` before choosing full, delta, patch, audit, or repair routes.
- Use `recover_storyboard_handoff` only for a registered capability gap and a current full-regression certificate. The two phases require two different server-production work orders; the user may request both from any authenticated window, and each must be exactly `rule_improvement + execute + explicit_execute`. Backfill targets must equal the gap, corresponding handoff IDs, and `controlled_phase:preflight_evidence_backfill`; recovery targets must equal the gap, corresponding handoff IDs, and `controlled_phase:handoff_recovery`. If a cached host omits or sends `null` for `phase`, validate the authenticated namespace and exact production authority first, then infer only from one unique recognized token; omission never means a default recovery phase. Missing, duplicate, multiple, unknown, drifted, mixed, or otherwise extra targets must fail before plan generation or mutation. For an eligible immutable legacy handoff missing production-preflight fields, plan first, then execute the identical list/`plan_sha256` with `REVALIDATE_AND_APPEND_PRODUCTION_PREFLIGHT_EVIDENCE`. Only this guarded route may accept either an exact signed 0.5.4/current projection, or the exact 0.5.3 baseline whose eight-column canonical sidecar, short ten-column header, and every visible row reproduce under the frozen 0.5.3 projector. Seal projector/provenance and raw XLSX, canonical, old-handoff, old-production-certificate, and original-production-trace hashes into the proof; general `extract_xlsx` remains strict.
- The 0.5.12 historical-contract exception is limited to `GAP-1bb91d83751b422f` and the exact ordered six IDs in `UPGRADE_0.5.12.md`. Their frozen report must exactly match the signed original PASS/zero-issue report. For the real current FAIL report, each handoff must exactly match its own sealed canonical SHA, complete normalized report SHA-256, shot/error/warning counts, complete error-code histogram and current validator composite/full SHA-256; the six profiles are non-interchangeable, and any drift fails before mutation. Preserve that complete report and emit only `controlled_historical_production_preflight_attestation` / `historical_production_preflight_attestation` with `historical_contract_pass`; never claim current production pass. `HISTCACHE` is a separate, non-reusable proof domain, and the successor must receive a full current independent audit. After all six are attested, recover the exact ordered 11 IDs under `GAP-0e5d48969c4c494e`: plan first, then execute the identical list/hash with `SUPERSEDE_AND_REISSUE_PRESERVE_AUDIT`. Recovery preserves every old record as `superseded`, issues one `prepared + PENDING_AUDIT` successor per item through a signed CAS journal, and never modifies source artifacts or creates/reuses an independent-audit verdict.
- In 0.5.15, a signed recovery successor may itself be recovered after a later deployment changes the complete runtime dependency fingerprint. Register a new gap for the exact successor list and create a new exact recovery work order. Before plan, verify the immediate committed recovery journal and its signed old/new/certificate/trace after-images, unique Hub projections, original recovery work-order authority, immutable content fingerprints and current validation. For a historical successor, also require exact equality of its `HISTCACHE`, frozen PASS/zero report, complete current FAIL report hash/count/histogram and current validator identity; keep `current_production_pass_claimed=false` and require a full independent audit. Any lineage or evidence drift fails before writes. Execute remains append-only, produces only `prepared + PENDING_AUDIT`, and exact retries reuse the same successor.

## Standard route

1. `get_agent_status(project_id?)`; verify window-neutral access and use the current authenticated window for the required next operation. A pending independent audit still selects the audit route and blocks a new production batch, but no window switch or permission recovery is required. Use continuation only when the server identifies a stored 0.5.13-or-earlier legacy window-bound work order.
2. If and only if status is `migration_required`, run `migrate_project_state(action="plan")`, inspect the compatibility report and before/after hashes, then run the explicitly authorized `migrate_project_state(action="execute")`; historical artifacts stay immutable. Obtain a valid executable status before continuing.
3. `create_project(project_name)` only when no matching project exists.
4. `begin_project_task(...)` for every request.
5. Before storyboard authorship, call `query_project_issues(...)` and bind its active prevention-profile hash to the task. Known patterns are identified across episodes, files, shots, batches, and versions; those fields are occurrence locations rather than dedup identity.
6. `import_source_file(...)` once per unchanged source fingerprint and `read_project_artifact(...)` for required content; automatic bulk is the default for long content, and `if_none_match` avoids re-reading unchanged content.
7. For novel/chapter conversion, finish complete reading and build the conditional `source_ingestion` evidence before planning shots.
8. `plan_change_request(...)` before script/storyboard add, modify, delete, replace, merge, split, or move.
9. Generate or rewrite within the locked scope. Before accepting each scene, compare its dialogue occurrence inventory against the server-derived source-dialogue authority manifest; exact text, punctuation, order/segmentation and uniquely resolved speakers must close at 100%. After each complete scene, call `preflight_storyboard_draft(scope_kind="scene")`; a failed or ambiguous scene is repaired and preflighted again before downstream generation. Failure is persisted as a draft-preflight ledger event but creates no artifact, version, XLSX, projection, successor, or handoff.
10. For a first full draft, invalidated complete scene/episode, or any dialogue/speaker change, call `preflight_storyboard_draft(scope_kind="full")` on the exact final canonical. Only its signed, full-scope, commit-ready `draft_preflight_id` may authorize `commit_storyboard(..., draft_preflight_id=...)`. Use `commit_storyboard_delta(...)` only for an authorized same-identity/same-count visual or other non-cognitive execution change whose exact dialogue text, punctuation, order/segmentation, speaker identity, source mapping, cognition, and protected-dialogue evidence remain unchanged; supply exact base hashes, stable UIDs, target range, neighboring boundaries, refreshed shot-bound evidence, and only changed complete 27-field records. Psychological audio and any insertion/deletion/movement/split/merge/renumber or source/cognition/boundary/topology change also use the full route. Both commit routes save a compact canonical JSON/XLSX, production preflight, signed handoff, and honest server-only trace without claiming independent audit pass.
11. `commit_project_artifact(...)` for plans, scripts, dialogue, anchors, keyframes, BGM, voice, statistics, conversion, or production packages; do not use it to pre-generate a duplicate Seedance/batch narrative. Use `complete_task_validation(...)` for every non-storyboard deliverable.
12. From any authenticated window, call `audit_storyboard(...)` using a distinct server independent-audit work order; atomically consume the exact handoff, reuse only objective facts, and independently recompute all eight quality layers. For repair return, invoke the exact original audit authority root even if the user window changed. When the exact independent-audit cache does not hit, submit `semantic_audit` under `semantic-audit-v2-compact-master`, bound to the canonical hash and reviewed shot count, with exactly eight unique layer records, concrete evidence IDs, targeted issues/actions, and a consistent conclusion. Audit must not regenerate any shot, projection, Seedance prompt, or batch.
13. `signoff_task(...)` only after the exact clean independent-audit certificate exists and the user explicitly approves or asks to reopen.

The first-draft production grade requires overall correctness and direct usability of at least 98%, every episode at least 96%, and new local issue rate of at most 2%, with zero hard errors, major issues, known-issue recurrences, or systemic duplicate patterns. This grade measures prevention quality and never relaxes a gate: full preflight becomes commit-ready only with no outstanding issue. Final independent audit requires all eight layers at 100%, with blocking, residual, and introduced counts all zero.

## Audit and repair route

- `audit_only`: audit the whole artifact once and report only the independent result; do not modify it.
- `audit_and_repair`: the original audit authority first issues an immutable certificate and problem package. Only then create the conditional repair authority; the user may request it from the same window. For certificate-confirmed non-structural shot fields, use `commit_storyboard_patch`; structural/boundary/cognition/source/order/timing/topology/core-plan repair uses the package-bound full `commit_storyboard` rebuild of the complete affected scene or episode. `commit_storyboard_delta` is production-authorized for user-directed changes, not a repair-authority shortcut. Every route creates a full new JSON/XLSX and runs all 49 validators, G0–G13, THG-01–THG-12 and multiline round-trip checks.
- A repaired version always returns through the signed `repair_to_audit` handoff to the same original audit authority root and audit cycle. Any authenticated window in the same namespace may invoke that exact root. Repair/preflight cannot sign itself off, and another audit root cannot consume it.
- A forced re-audit uses a fresh server-minted single-use successor handoff and distinct route/event traces; it never rewrites or reopens a consumed root. Every blocking issue must resolve to at least one canonical shot. Only the newest completed failed lineage's signed package may be consumed; an older package is superseded even if its signature remains valid.
- A modern certificate binds the exact ledger event SHA. Every successor binds its parent's certificate HMAC and event SHA, and storage verifies the bridge under the project lock. A legacy certificate without the event SHA cannot replay or authorize sign-off; it may only parent an explicit forced re-audit, and becomes historical only after that modern successor completes.
- A failed artifact cannot be relabelled PASS by submitting a new semantic report against the same file/source_version/artifact/canonical bindings. It must first produce a package-bound repaired artifact and fresh handoff, then return to the original auditor. Exact crash recovery may complete an event-only half-write only for the same normalized semantic/event/trace/fingerprint identity. The only case normalization is lowercasing a valid 64-hex caller `semantic_audit.canonical_sha256`; replaying that SHA in another hex case returns the same receipt without another successor/event/certificate/round, while every other field remains exact. The certificate must equal the complete deterministic certificate binding, not merely carry a valid HMAC; even a validly re-signed mismatch, certificate-only state, different semantic or stale lineage fails closed with zero authority/projection mutation. Repair-package replay accepts only a zero-downstream `issued` state or a fully closed `consumed` state with exact repair work order, successor/base CAS, metadata, return handoff and Hub projection. A consumed package may return to `issued` by compensation only when the original repair claim token and generation match, the fixed base successor transaction is already `aborted`, the signed handoff and Hub projection are both `rejected + aborted`, and there is no claim/consumption/audit-certificate or other independent-audit downstream reference. Any prepared/committed transaction, different claim, published/live handoff or audit downstream forbids release. `consuming`, forged terminal state, or a missing package with downstream evidence is corruption. Recovery runs under the same storage lock after rechecking latest lineage, exact certificate HMAC, zero downstream evidence and the fenced single-finisher claim; completed replay is otherwise read-only and cannot resurrect a package or return stale authority.
- The result is clean only when blocking errors, residual issues, and introduced issues are all zero.
- Reuse a prior independent result only when canonical, raw artifact, source, boundary, ruleset, validator and audit-class fingerprints all match. A production preflight never satisfies the first independent audit.
- At round three, stop local patching and return the upstream-rebuild blocker.

## Efficiency without lowering quality

- Delta changes reduce authored/transferred content, not validators: the model authors each semantic fact once in the 27-field compact record; actions, expressions, dialogue, delivery, listener reaction and the required three Seedance 2.5 stages exist only in `画面内容`, while `音色` and the four lighting fields remain explicit. The server computes episode-local cumulative timing/batch statistics and projects the R10-SPC-1 formal cell plus static GPT keyframe instruction only at export, runs all 49 validators, G0–G13, THG-01–THG-12 and the multiline XLSX round-trip, and hands the compact artifact to all eight audit layers.
- Production, audit, repair, cache warm-up, and background jobs must never pre-generate or persist Seedance text, `batches`, a Seedance column, or a generated-batch sheet. Legacy forms are read-only migration inputs; new versions never write retired fields back.
- Production owns canonical authorship and must correct a failed draft before commit. Deterministic code owns projection, validation, certificates, hashes, state transitions, and failed-draft learning. Independent audit owns only the read-only omission search and final semantic verdict; it is not a cleanup stage for known generation or template defects.
- Automatic 16,000-character bulk reads reduce long-source tool-call count while preserving exact-order, no-gap reconstruction.
- Tool traces cover MCP server time only. Report ChatGPT planning/generation as unmeasured unless the user explicitly requested the 0.5.3-or-newer no-API diagnostic and a complete five-checkpoint `mark_performance_stage` run exists. That diagnostic reports `tool_bracketed_chat`, not exact end-to-end time; never infer total chat duration from a fast server trace.

### Explicit no-API diagnostic exception

- Load `no_api_performance_diagnostics.md` only for a user-requested native ChatGPT timing investigation. Ordinary production, audit and repair must not pay for five extra marker calls.
- After the role-specific work order exists, record exactly `task_started → inputs_ready → plan_ready → canonical_ready → delivery_ready`. Use only server timestamps, IDs, enums and bounded counts; never submit source, prompts, dialogue, shot text, credentials, user identity or hidden reasoning.
- Link the persisted production/audit/import telemetry IDs actually returned by this run. Their duration remains `server_only`; the gaps between diagnostic markers are `tool_bracketed_chat` and may contain model work, client transport and orchestration.
- A single run locates the dominant observed interval but cannot prove a thinking-mode effect. Compare reasoning modes only with a user-authorized matched run that keeps source, scope, route, shot count, cache state, window type and R10-SPC-1 deliverables fixed.
- Diagnostics do not authorize removal of per-shot `空间站位描述`, environment, sound, performance/dialogue, `生成限制`, or any of the four lighting fields; all validators, gates and independent audit layers remain active.

### Fast-safe call discipline

- An ordinary content task with a matching runtime-test certificate must not inspect plugin source, rerun bootstrap/golden/Agent suites, or rebuild system rules. `get_agent_status` verifies the certificate once.
- Use the plugin's authenticated project hub and issue ledger for ordinary content tasks. Do not materialize or rewrite the global Library hub/ledger unless the request is a system/rule update, explicit shared-ledger task, or final archival synchronization.
- For an unchanged imported source, use its stored fingerprint and canonical evidence. Do not download or page through the same file again merely to restate production facts; a fingerprint mismatch or a genuinely missing semantic excerpt is the only reread trigger.
- A bounded production replacement normally needs `get_agent_status` → `begin_project_task` → `plan_change_request` → one `commit_storyboard_delta`. Add one automatic bulk read only when the changed semantic content is not already available. Full generation still uses the full route.
- A clean independent audit normally needs `get_agent_status` → one read-only audit work order → one `audit_storyboard` call against the signed handoff. On a cache miss, the audit chat reviews the canonical and supplies the eight-layer semantic evidence in that call while the service independently recomputes machine validators; on an exact cache hit the prior signed evidence is reused. The chat must not regenerate shots, repeat production preflight, or expand the complete workbook into prose.
- A failed audit may add the conditional repair chain only after authorization: one repair work order → one package-bound patch/full commit → one return audit by the original audit root. Do not pre-generate repair content; no extra user window is required.
- Keep intermediate chat updates brief and return IDs/hashes instead of echoing complete canonical rows. If the safe route needs extra reads or retries, record the concrete cache miss, fingerprint change, missing input, validator failure, or transport error that caused them.
- Do not call `mark_performance_stage` on this ordinary fast-safe route. It is an opt-in diagnostic wrapper, not a required production dependency.

## Cross-chat continuity

Continuity comes from the MCP data store, authenticated user namespace, stable `project_id`, and signed authority-root/epoch records; it does not come from reading inaccessible chat history. The MCP stores project state, versions, deliverables, audit events, recurrence, capability gaps, and active authority generations. In cloud mode, use persistent storage and OAuth so different users cannot share a namespace. Every trusted window in the same namespace has equal orchestration access; server work-order identities preserve production/audit/repair separation. Pending independent audit continues to block a new production batch until audit closes, while the current window may perform that audit directly.

## Brief user-facing audit format

- Clean: `审计通过｜阻塞错误0｜原问题残留0｜修改新增问题0`
- Failed: `审计未通过｜共N项` followed by short numbered items with shot IDs and one-sentence fixes.
- Blocked: one sentence naming the blocker and next action.
