# Conditional legacy authority compatibility

Read only for an explicitly identified legacy record/recovery task. Current 0.5.24 work orders are window-neutral. The following preserved compatibility contracts never authorize new user-window restrictions or historical data changes merely because the plugin is upgraded.

## Backfill legacy evidence and recover stale handoffs through the controlled route

Keep the public tool set at exactly 19 and read `references/plugin_execution.md` before using `recover_storyboard_handoff`. Require a registered capability gap, a current full-regression certificate, and two different server-production work orders: one for evidence backfill and one for handoff recovery. The user may request both from any authenticated window, while each work order receives a distinct server execution identity and must be exactly `rule_improvement + execute + explicit_execute`. The backfill work order targets must be the exact gap, corresponding handoff IDs, and machine-readable token `controlled_phase:preflight_evidence_backfill`; the separate recovery work order must target the exact gap, its corresponding handoff IDs, and `controlled_phase:handoff_recovery`. Missing/extra targets, a wrong phase token, another authenticated namespace, or reuse of one work order across both phases must make `action="plan"` fail with `scope_mismatch` and zero writes.

Plugin 0.5.9 and later supports hosts whose cached tool schema cannot send `phase`. If `phase` is omitted or `null`, the service must first validate the current transport session and the exact production work-order authority, then infer only from one unique recognized `controlled_phase` target. Missing, duplicate, multiple, unknown, case/whitespace-drifted, or mixed phase targets must fail before plan generation or mutation. An explicit phase must still match the exact target set; omission never means a default recovery phase.

Plugin 0.5.10 introduced historical-workbook revalidation only inside this guarded backfill/recovery route, and 0.5.12 preserves that boundary. Accept either an exact signed 0.5.4/current projection contract, or the exact legal 0.5.3 baseline combination: an eight-column canonical sidecar envelope, the short ten-column formal header, and every visible row reproduced byte-for-byte after NFC/LF normalization by the frozen 0.5.3 projector. Bind the resulting proof to the raw XLSX SHA, canonical SHA, old handoff, old production certificate, and original production trace. Reject any cell, header, sidecar, signature, provenance, or lineage drift before mutation. Do not relax general `extract_xlsx`, rewrite or normalize the workbook, or use this compatibility for ordinary import/audit.

For an immutable legacy `prepared production_to_audit` handoff that lacks eligible production-preflight fields, use only the backfill work order to call `phase="preflight_evidence_backfill", action="plan"`, inspect every item and `plan_sha256`, then execute the identical list and hash with confirmation `REVALIDATE_AND_APPEND_PRODUCTION_PREFLIGHT_EVIDENCE`. The ordinary route still requires a zero-issue current validator report before it may append signed `production_preflight` evidence. The only exception is gap `GAP-1bb91d83751b422f` with this exact ordered list: `HND-f6fd29730a074d2c`, `HND-95e3b1c141a64783`, `HND-c88ee199d5fb4676`, `HND-e8ca409208134104`, `HND-0dd8fa51a9e24cd0`, `HND-9029110f35d74270`. For those six, the frozen historical report must be PASS with zero issues and exactly equal the original signed production report. Plugin 0.5.12 no longer accepts a category-level “aspect wording only” predicate for their real current FAIL reports. Each handoff instead has one sealed, non-interchangeable profile that binds its canonical SHA, complete normalized current-report SHA-256, shot/error/warning counts, complete error-code histogram, and current validator composite plus full SHA-256; plan and execute must rerun the current validator and match every field exactly before any authoritative write. Preserve the complete matched current report as `fail_current`. Append only a `controlled_historical_production_preflight_attestation` with certificate class `historical_production_preflight_attestation` and status `historical_contract_pass`; set `current_production_pass_claimed=false`, `current_preflight_cache_reusable=false`, `conclusion_reusable_for_independent_audit=false`, and `requires_full_current_independent_audit=true`. Use the separate `HISTCACHE` domain and never reuse it as current-preflight or independent-audit evidence. Do not rewrite the old handoff/certificate, reconstruct a first-draft grade, or change storyboard/canonical/XLSX/history bytes. Any profile, historical/current report, provenance, validator or authored-content drift fails closed. Read `../../docs/UPGRADE_0.5.12.md` for the current sealed-profile contract; the 0.5.11 aspect-only wording is retained only as corrected release history.

After all required evidence exists, use only the separate recovery work order to recover a handoff blocked solely by its stale complete dependency fingerprint with `phase="handoff_recovery"`: plan first, then execute the identical list and hash with `SUPERSEDE_AND_REISSUE_PRESERVE_AUDIT`. For gap `GAP-0e5d48969c4c494e`, the ordered recovery list must be exactly `HND-5394638be5fe4a55`, `HND-ea122cf3048e482a`, `HND-3a090b4f44c74929`, `HND-c765ba78aab840ff`, `HND-7738fa25ce4044c9`, followed by the six historical-attestation IDs above. The signed CAS journal preserves each old record as `superseded`, issues exactly one current-fingerprint successor, and leaves it `prepared + PENDING_AUDIT`. A historical attestation remains only provenance and current-failure diagnosis; every successor requires a full current independent audit. Neither phase deletes history, reuses an audit conclusion, signs an independent-audit verdict, or lets production claim independent-audit pass.

Plugin 0.5.15 also permits a signed `prepared + PENDING_AUDIT` recovery successor to be recovered again after a later deployment invalidates its complete dependency fingerprint. Register a new capability gap for the exact successor IDs and use a new exact recovery work order; never reuse the original exact-list gap as a wildcard. Before plan, require the immediate signed recovery journal to be committed and to reproduce its old/new/certificate/trace after-images and Hub projections; require the recorded recovery work order to be server-production `rule_improvement + execute + explicit_execute`; and revalidate every immutable content fingerprint. An ordinary successor must still carry a valid zero-issue current production certificate. A historical successor must preserve the exact signed `HISTCACHE`, frozen PASS/zero report, full current FAIL report hash/count/histogram, current validator identity, `current_production_pass_claimed=false`, and `requires_full_current_independent_audit=true`. Any lineage, authority, report, certificate, trace, content or projection drift fails before mutation. Execute remains append-only and idempotent: the direct predecessor becomes `superseded`, the new record stays `prepared + PENDING_AUDIT`, and no independent verdict is issued or reused. Read `../../docs/UPGRADE_0.5.15.md` before using this successor route.

For historical Hub projection reads, 0.5.8 accepts only one of two exact JSON shapes: the signed handoff with `record_id`, `project_id`, and `integrity_hmac` removed, or the complete signed handoff including that envelope. Any extra, missing, altered, or mixed field fails closed before mutation. This is read-only compatibility: never migrate or rewrite a historical row merely to normalize its shape. All future production Hub writes use the stripped projection.


## Preserve 0.5.13-and-earlier authority rotation only as legacy compatibility

Do not use continuation for a 0.5.14-or-later window-neutral work order. For a stored 0.5.13-or-earlier window-bound work order only, continuation remains cloud-only and applies only to the exact role matrix: production `storyboard_create|storyboard_regenerate|storyboard_change`, independent audit `storyboard_audit`, and repair `storyboard_repair`. Do not offer it for `rule_improvement`, version management, another production-classified operation, or an arbitrary unfinished work order. When one eligible legacy work order is still bound to an unavailable chat window, use only the server's safe role-continuation projection; never infer legacy permission from remembered chat text, a caller-supplied role, `window_key`, or an inaccessible conversation. A continuation restores the same logical authority and exact work-order contract. It does not create another role, change status or authorization, widen scope, close an audit, or bypass a project blocker.

Use `begin_project_task` with `action="plan_role_continuation"` for exactly one `resume_work_order_id`. The service must derive the role from that eligible work order and require the submitted operation, mode, authorization, ordered targets, source lock, protected scope, and expected outputs to match it exactly. Inspect the returned stable `authority_root_id`, role, contract and pre-state hashes, current/next generation, `new_binding_status`, and `plan_sha256`. Plan is zero-write in 0.5.11 and has no TTL claim. Its hash binds the work-order contract/snapshot, current authority head, target server-observed session and runtime certificate. Then call `action="execute_role_continuation"` with the identical request, the exact plan hash, and confirmation `ROTATE_WINDOW_AUTHORITY_REVOKE_PREVIOUS_SESSION`.

Before both plan and execute, reject with zero writes while the authority owns a live operation lease or an unexpired handoff, repair-package, or draft-preflight commit claim. Every authority-operation lease is strictly exclusive per logical authority root: a second request for the same root returns `authority_operation_in_progress` even when work order, session and payload match; never join, share holders or execute those calls concurrently. Different authority roots may operate in parallel. An expired lease may permit rotation without rewriting that lease. Expiry of a draft-preflight commit claim only removes the rotation blocker: its preflight certificate remains bound to the old session, so the continued session must obtain a new current-session preflight rather than reclaim it. For repair, require the current signed package and a fenced consumption claim with token, monotonically increasing claim generation, and bounded lease; a legacy 0.5.10 `consuming` package without the complete lease fields fails closed and is never auto-migrated by continuation.

Execution appends one signed continuation and moves the unique active head to a new server-observed physical window/actor/session epoch with the next generation under the same authority root. This logically revokes the preceding generation; do not claim that the service rewrites the old signed generation to store `revoked`. Preserve every historical work-order, continuation, handoff, certificate, trace and binding byte. Every subsequent authority write must recheck the active generation at its next persistence boundary, so an old or in-flight context fails before committing after the head advances. Only newly issued handoffs, repair packages, and other records whose current Schema explicitly defines authority fields persist root/epoch/generation; consumption claims use their separate token/generation/lease contract, and no certificate or trace is retrofitted merely for continuation. A same-target exact replay returns the same continuation and epoch with `idempotent_replay=true` only after the first exclusive operation has ended and while that continuation is the active head (or while completing its signed-record-to-Hub half-write); it is never a concurrent same-root join. After a later generation advances, reject the old replay as superseded. A changed work-order contract/snapshot, target session, runtime certificate, or authority head makes the computed plan stale; live claims are separately rechecked but completed claim, handoff, or certificate changes are not universally part of `plan_sha256`.

Fence every ordinary handoff, repair-package, and independent re-audit-successor claim to the claiming work order's currently active authority root, generation, and server-observed session, plus an exact claim token, monotonically increasing claim generation, and live bounded lease. Recheck all of those bindings under the project lock for finish and release. An old epoch, superseded token/generation, expired lease, or old-session retry must fail without changing signed storage or Hub. Lease expiry permits only a new claim under the current active epoch with a fresh token and next claim generation; it never revives the expired token. Finishing an ordinary handoff additionally requires the real signed `independent_audit` certificate stored by the service and exactly bound to that handoff, audit work order, and artifact. A caller-provided certificate name, production preflight, unsigned record, or mismatched certificate is not completion evidence.

Never let delayed successor-candidate publication rewrite a signed handoff that has already moved to `consuming` or `consumed`. It may close only the candidate artifact's publication transaction while preserving the exact signed handoff bytes and Hub projection, including claim history/token/generation and any audit-certificate binding. A `passed` audit work order is normally terminal for continuation. Permit its narrow recovery exception only when the same audit authority has exactly one service-signed `prepared` `independent_audit_successor`; classify the plan as pending-successor recovery and let the new active epoch claim only that existing route. Zero, multiple, unsigned, non-prepared, or differently bound successors must fail without reopening the passed audit, minting another route, or changing its verdict.

For legacy continuation only, never rotate across roles. A session that belongs to a legacy production authority history cannot continue legacy independent audit or repair for that workflow, and a legacy audit session cannot continue legacy repair. This restriction does not assign a role to a 0.5.14 user window. A repaired successor still returns to the original independent-audit authority root and audit cycle. Pending independent audit remains blocking for a new production batch, while the user may complete that audit from any authenticated window.

The currently identified eleven invalid legacy `prepared production_to_audit` handoffs are not recovered merely by window-neutral orchestration. Do not report implementation, documentation, validation, or deployment as their backfill/recovery. They still require the separate two-work-order controlled backfill and recovery route under a current runtime certificate, after which only the server's independent-audit authority may consume the replacements. The user may request each phase from the same window; the production execution identity still cannot sign the audit or act as repair.
